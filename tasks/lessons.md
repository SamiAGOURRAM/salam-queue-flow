# Lessons

- When mocking `react-i18next`'s `useTranslation` in tests, hoist the `t` function to a stable reference (`vi.fn()` or module-level const) instead of creating it inline. An unstable `t` reference in the component's `useEffect` dependency array causes an infinite re-render loop: effect fires -> promise resolves -> state update -> re-render -> new `t` -> effect re-fires -> ...

- When review feedback flags hardcoded UI strings in clinician workflows, immediately check print templates and datalist suggestion constants for i18n coverage in all active locales.
- For multi-row writes in clinical sections, avoid sequential per-item persistence; prefer single-statement batch writes (upsert/insert) to reduce partial-save risk.
- If localStorage is used for medical entry suggestions, include age-based pruning from day one to prevent stale long-tail suggestions.
- For clinician-facing validation/conflict feedback, emit stable error codes from service/repository layers and localize only at UI boundaries to avoid hardcoded language leaks.
- In rich editor systems, avoid `unknown` and escape-hatch casts (`as never`) for document content and node attributes; define explicit JSONContent-based models and typed attribute interfaces before wiring repository/UI flows.
- When using monkey-patched E2E harnesses for deterministic UI coverage, always pair them with at least one non-mocked regression lane (full E2E sweep and/or DB-backed verification) to preserve real-world confidence.
- For queue/role behavior requests with ambiguous semantics (owner vs doctor vs receptionist scope), pause implementation and lock product semantics + scope matrix first; code only after plan sign-off.
- For authorization-sensitive mutations, do not reuse broad clinic-management helpers for owner/admin-only operations; enforce explicit role predicates at both RPC and RLS mutation layers, then verify under authenticated role context in smoke SQL.
- When queue scope is enforced server-side, every schedule consumer (calendar, dashboard, queue list) must pass scope context explicitly; relying on clinic-wide defaults will break provider/restricted users.
- For view-only permission modes, disable form controls in addition to save actions so non-manager users cannot appear to edit critical settings.
- On local PG17, avoid helper-function predicates inside new RLS policies when an equivalent inline EXISTS predicate is possible; helper-based policy checks can destabilize authenticated evaluation paths.
- For scope-aware queue consumers, never fetch with default scope assumptions before `useQueueScope` resolves; guard fetches on resolved requester staff context and provide non-owner personal-scope fallback on scope errors.
- In clinic team UX, separate authorization identity (`clinic_owner`) from clinical role (`doctor`/provider); owners can be clinicians, but owner privileges and owner labeling must stay explicit across role and queue-access displays.
- Do not assume local Docker admin implies remote Supabase cloud admin; always verify explicit staging credentials (CLI token/service-role/DB URL) before promising remote execution.
- Before proposing staging/cloud verification steps, explicitly confirm whether the user runs cloud at all; if local-only, switch immediately to Docker-Supabase local go/no-go workflow.
- For clinician-facing selectors and settings copy, never surface raw IDs or internal jargon; prefer profile full names plus plain-language phrasing, and ship EN/FR/AR key parity in the same change.
- In clinic team and override UIs, phrase queue permissions in user language ("own queue" / "all doctor queues") and avoid scope jargon; when owner has implicit clinic-wide privileges, do not expose owner-self in doctor-specific override selectors.
- In multi-doctor live queue UX, a binary `all/my` scope toggle is not enough for owners; include explicit per-doctor queue entry points (selector options and/or doctor rows) with a clear general-view fallback.
- For async option-loading effects that depend on i18n/context callbacks, avoid unconditional state writes; compare previous and next option arrays before setting state to prevent render loops and hanging tests.
- In hook-driven data flows, never pass freshly created array/object literals as scope/filter props on every render; memoize derived filters (`allowedStaffIds`, mode options) so effect dependencies do not trigger infinite refresh-loading loops.
- In stateful queue selectors, avoid selected-label copy that sounds like loading progress; use explicit active-state wording and provide a one-click path back to general view to reduce "stuck" user reports.
- In clinic settings, do not use a single global `manage_clinic_settings` gate for every tab; section-scoped permissions (like doctor-overrides) must be evaluated independently so owner-granted doctor capabilities are not blocked by unrelated global settings rights.
- For doctor-overrides, do not infer provider eligibility from role strings like `includes("doctor")`; use normalized role definitions and `baseRole` so custom doctor roles stay editable.
- If `clinic_staff` remains owner-update-only at RLS level, doctor self-override saves must use a narrowly scoped SECURITY DEFINER RPC that updates only override columns with explicit owner/self-provider authorization.
- In doctor-overrides UI gating, do not tie self-edit authorization to the first matching own provider row; allow any selected provider profile owned by the authenticated doctor and keep a self-provider fallback query path for non-manager users.
- In mixed read-only/editable settings pages, use explicit visual affordance (for example success-green borders/badges) on editable doctor override sections; relying on default muted card styling causes users to assume everything is locked.
- In slotted queue UI, do not re-filter backend day-scoped schedules by local `today` or rebuild date keys with `toISOString`; local timezone shifts can hide valid appointments while summary counts still show waiting patients.
- In `ClinicQueue`, do not mount `EnhancedQueueManager` for non-owner staff until queue scope resolves (`resolvedScope.requesterStaffId === staffProfile.id`), otherwise an initial unauthorized clinic-wide RPC can fire before personal/restricted scope takes effect.
- When the user reprioritizes roadmap work (for example, de-prioritizing referrals for role enforcement), stop the previous track immediately and execute the new priority sequence before adding optional follow-up scope.
- For SQL smoke scripts that perform direct DML against RLS-protected tables, always `SET LOCAL ROLE authenticated` (or another non-bypass role); setting JWT claim values alone while running as postgres can silently bypass RLS and produce false-positive authorization checks.
- MCP high-level `Server` request handlers (ListTools/CallTool) do not receive the underlying HTTP request, so per-user auth can't be read there directly; carry the bearer token from the transport layer into handlers via `AsyncLocalStorage` and resolve `AuthContext` inside the handler. Scope `tools/list` with `getAccessibleTools(context)` so callers only see tools they may invoke.
- Docker dev pattern that mounts source + shields `node_modules` in named volumes will keep STALE deps after you add a package, because named volumes only seed from the image when empty. After adding/removing dependencies, run `docker compose down -v` before `up --build` so the volumes re-seed from the freshly built image.
- Demo/seed data for queues must be date-relative AND self-refreshing: appointments stamped with `CURRENT_DATE` at seed time go stale when the day rolls over, leaving "today's queue" empty (looks like "call next is broken"). Put the volatile daily seed in a SECURITY DEFINER function (`refresh_demo_queue`) granted to `anon` and call it on demo entry; seed the persona users once via the admin API.
- MCP tool queries must run under the caller's JWT (anon key + `Authorization: Bearer <jwt>` client), not the service-role key: service-role bypasses RLS AND makes `auth.uid()` NULL, so SECURITY DEFINER RPCs that check `auth.uid()` (call-next, booking) fail over MCP. Route `@queuemed/core` through a per-request JWT-scoped container; keep service-role only for trusted JWT validation.
- "Dark goes dark then snaps back to light" = an effect calling `setTheme('light')` (here `useForceLightMode`) fighting the toggle. For global dark mode, neuter the force-light hook, show one always-visible toggle, and tokenize hardcoded `bg-white`/`text-gray-*`/`text-black` on public pages to `bg-background`/`text-foreground`/`bg-card`/`border-border`.
- When wiring the Vercel AI SDK (v5) to MCP, the most version-stable path is the MCP SDK `Client` + `StreamableHTTPClientTransport` (forward the user's JWT via `requestInit.headers`), then wrap each MCP tool as an AI SDK `tool({ inputSchema: jsonSchema(mcpTool.inputSchema), execute })`. Avoid the churn-prone `experimental_createMCPClient` for production.
- When creating seed data with `clinic_staff`, remember `user_id` is NOT NULL and references `auth.users(id)`. You MUST INSERT auth users first (with fixed UUIDs) before inserting clinic_staff rows.
- When inserting into `public.profiles`, `phone_number` is NOT NULL with no default. Always provide it alongside `full_name`.
- Patient-facing booking flow needs RLS policies on BOTH `clinic_staff` and `profiles` to allow public SELECT of active staff. A policy on clinic_staff alone is insufficient because BookingFlow also queries `profiles.full_name` for doctor display names.
- When data "doesn't show up" for patients but exists in the DB, the first suspect is RLS blocking the read. Query with direct SQL to confirm data exists, then check pg_policies for the relevant tables.
- A vague assistant apology in the chat ("unable to find clinics in Casablanca… try again later") together with an mcp-server log `TypeError: fetch failed` (e.g. `ClinicRepository.search`) means **local Supabase is DOWN**, not a bug in the AI/MCP/auth chain (which had already run: tool selected, auth resolved to anonymous, RBAC passed). mcp-server reads `SUPABASE_URL=http://host.docker.internal:54321`; if `:54321` is unreachable, `npx supabase stop && npx supabase start` (data volume persists — the Casa Family Care / Casablanca seed is already there, no re-seed needed). A db container that exited 137 after a host shutdown leaves a stale "already running" state that needs the `stop` first. Verify container→DB with `docker compose exec mcp-server node -e "fetch('http://host.docker.internal:54321/rest/v1/').then(r=>console.log(r.status))"` (curl/wget aren't installed in that image; node's fetch is what the app uses).
- In patient dashboard "Upcoming" filters, don't use date-based filtering (`aptDate >= today`) for active queue/scheduled appointments. An appointment that is currently #2 in queue or scheduled is always "upcoming" for the patient, even if its original date was yesterday (seed data, midnight rollover). Filter by status alone: any appointment with an active status is upcoming.
- For public shareable tokens (queue status links), don't require strict `patients.user_id = auth.uid()` ownership. The token only exposes public queue status (position, estimated time), not PHI. Allow token generation for unlinked patient records (`user_id IS NULL`) since there's no owner to authorize.
- `@queuemed/core` compiles with `moduleResolution: "bundler"`, so it emits **extensionless** re-exports (`export * from './types'`). A NodeNext consumer (`apps/mcp-server`, `apps/chat-api`) with `skipLibCheck: true` then sees **zero exports** from any *directory* barrel — no error, the members just vanish. To import a core symbol into mcp-server, the re-export chain must carry explicit `/index.js` (directory) and `.js` (leaf) all the way to the source file. RESOLVED: core was switched to `module/moduleResolution: NodeNext` and all relative specifiers given explicit `.js`, so consumers now see real types and `node dist/index.js` runs. (mcp-server keeps its own `adapters/supabase/types.ts` — unification pending.) Diagnostic to remember: "no exported member" while `tsc --traceResolution` points at the right `.d.ts` = an extensionless re-export silently dropped under `skipLibCheck`.
- Each `packages/*`/`apps/*` TS package's `tsconfig.json` must list `"**/*.test.ts"` in `exclude`, or `tsc` build emits test files into `dist` (ships test code to prod). `@queuemed/core` already does this; `apps/mcp-server` did not until the first co-located test was added — mirror the sibling before committing.
- The `clinics` table column is `phone` (NOT `phone_number`), and the appointment status enum uses `waiting` (NOT `checked_in`). `BookingRepository.mapToClinic` reads `row.phone_number`, so `Clinic.phoneNumber` is always `undefined` app-wide (surfaced when typing repo rows with `Tables<'clinics'>`); fix the column name when next touching mapToClinic. Several mcp tools had compared status to the phantom `"checked_in"` (now corrected to `"waiting"`).
- Canonical Supabase `Database` types now live in `packages/core/src/types/database.ts` (re-exported via core's barrel); `apps/web/src/integrations/supabase/types.ts` is a thin re-export of `@queuemed/core`. Regenerate the schema INTO core, not web. mcp-server still has its own `adapters/supabase/types.ts` (not yet unified).
